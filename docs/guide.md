# Руководство пользователя

Пошаговый путь от установки до исправленных находок. Если хочется сначала
просто посмотреть, как это выглядит, запустите демо (1 минута, ничего не
нужно ставить, ваши файлы не затрагиваются):

```sh
python examples/demo.py --open
```

## 1. Установка

Нужен только **Python 3.11+**. Сам Scout не требует сторонних пакетов:
он запускает внешние инструменты (детекторы), которые уже есть в системе.

```sh
git clone https://github.com/Alpha-Oi/scout.git
cd scout
python tools/doctor.py --check     # что установлено, ничего не ставит
```

Пример вывода:

```
detector         status     via          required
------------------------------------------------------
pytest-failed    [ok]  ok    PATH         yes
pip-audit        [MISS]missing              yes
ruff             [ok]  ok    PATH         yes
todo-fixme       [core]built-in              yes
secrets          [core]built-in              yes

Ready: 6/14 detectors
```

| Статус | Значение |
|---|---|
| `[ok]` | инструмент найден, детектор будет работать |
| `[core]` | встроенный детектор, ничего ставить не нужно |
| `[MISS]` | инструмент не найден, **детектор будет пропущен** (не подделан) |

Хотите все 14 детекторов:

```sh
python tools/doctor.py          # спросит подтверждение и поставит недостающее
python tools/doctor.py --yes    # без вопросов (удобно в CI)
```

`doctor.py` ставит пакеты через `pip` (а `pyscn` через `uv`). Если не хотите
ничего ставить, Scout всё равно работает с тем, что есть: минимум это два
встроенных детектора, `secrets` и `todo-fixme`.

## 2. Первый скан

Одна команда делает всё: сканирует, формулирует предложения, строит дашборд и
открывает его в браузере.

```sh
python tools/scout.py ~/projects/my-app
```

| Параметр | Смысл |
|---|---|
| `--out DIR` | каталог отчётов (по умолчанию `./.scout`) |
| `--quick` | пропустить медленные `pytest-failed` и `pip-audit` |
| `--max-findings N` | общий потолок находок |
| `--llm` | предложения через [LLM](#7-предложения-через-llm-необязательно) |
| `--no-open` | не открывать браузер (удобно на сервере и в CI) |

Если для этого проекта в `--out` уже есть прошлый прогон, `scout.py` сам
посчитает diff с ним (см. [раздел 4](#4-повторный-скан-и-diff)).

### То же по шагам

`scout.py` просто вызывает инструменты из `tools/` по очереди. Если нужно
запускать их отдельно (например, повторить только `propose.py` с `--llm`):

```sh
python tools/scan.py  ~/projects/my-app --out ./reports   # 1. найти
python tools/propose.py ./reports/<папка-прогона>         # 2. предложить
python tools/render.py  ./reports/<папка-прогона>         # 3. собрать данные
cp tools/dashboard.html ./reports/dashboard.html          # 4. положить дашборд
python tools/sync.py ./reports                            # 5. вшить данные
```

> На Windows вместо `cp` используйте `copy tools\dashboard.html reports\dashboard.html`.

Папка прогона называется `<дата>-<имя-проекта>` (например `2026-10-11-my-app`),
её имя печатает `scan.py` в последней строке. Задать своё имя: `--run-name`.

Затем откройте `reports/dashboard.html` двойным щелчком. Сервер не нужен.

Что полезно знать про `scan.py`:

| Ситуация | Что делать |
|---|---|
| Большой проект, тесты идут долго | `--quick`: пропустит `pytest-failed` и `pip-audit` |
| Находок слишком много | `--max-findings 200` или лимиты в [`.scoutrc`](configuration.md) |
| Отчёты не должны попадать в репозиторий | `--out` вне проекта; по умолчанию это `./.scout` |

Scout **только читает** сканируемый проект. Все файлы пишутся в каталог
отчётов (`--out`).

### Что внутри папки прогона

| Файл | Что это |
|---|---|
| `findings.json` | все находки в едином формате |
| `proposals.json` | по одному предложению на находку |
| `scan.log` | что запускалось и что вернул каждый детектор (смотрите сюда, если детектор «молчит») |
| `meta.json` | путь к проекту |

`state.js`, `diff.json` и `dashboard.html` лежат уровнем выше, рядом с папками прогонов.

## 3. Как читать дашборд

Вкладки (**Diff** появляется, только если перед `render.py` был запущен `diff.py`):

- **По находкам**: плоский список, критичные сверху; есть фильтры по severity и категории.
- **По коду**: группы по правилу (`I001 × 450` сворачивает 450 карточек в одну).
- **Diff**: что нового, исправлено, сдвинулось, не изменилось по сравнению с прошлым прогоном.

В карточке находки: файл и строка, вывод детектора (**evidence**), предложение,
риск правки (`low|medium|high`) и трудозатраты (`S|M|L`).

Кнопки и клавиши:

| Действие | Как |
|---|---|
| Скопировать задачу для Claude Code | кнопка «Скопировать задачу» в карточке |
| Открыть в VS Code на нужной строке | ссылка «Открыть в VS Code» (`vscode://file/…`) |
| Поиск по файлу, заголовку, детектору, evidence | поле поиска, `/` фокус, `Esc` очистить |
| Экспорт в GitHub Code Scanning | кнопка «↓ SARIF» |
| Экспорт в issue / PR / чат | «↓ Markdown» или «Markdown в буфер» |

### Серьёзность и категории

| Severity | Как относиться |
|---|---|
| `critical` | разбирать сразу (например, похоже на живой секрет) |
| `high` | реальные баги и уязвимости, разбирать в первую очередь |
| `medium` | стоит исправить в ближайшее время |
| `low` | стиль, документация, мелкая чистка |

Категории: `bug`, `vuln`, `incomplete` (TODO/FIXME), `improvement`.

> Находка это **сигнал**, а не приговор. Детекторы бывают неправы (например,
> «секрет» оказывается заглушкой). Поэтому в каждой находке есть evidence:
> проверьте его глазами. Пометить ложное срабатывание можно через
> [`.scoutrc`](configuration.md) (`skip_detectors`, `severity_rules`).

## 4. Повторный скан и diff

После исправлений просто запустите ту же команду ещё раз: прошлый прогон этого
проекта в том же `--out` находится автоматически, а результат виден на вкладке **Diff**.

```sh
python tools/scout.py ~/projects/my-app
```

Вручную (например, для двух произвольных прогонов) делается так. **Порядок важен:**
`diff.py` должен выполниться **до** `render.py`, иначе вкладка Diff будет пустой.

```sh
python tools/scan.py    ~/projects/my-app --out ./reports
python tools/propose.py ./reports/<новый-прогон>
python tools/diff.py    ./reports/<старый-прогон> ./reports/<новый-прогон>
python tools/render.py  ./reports/<новый-прогон>
python tools/sync.py    ./reports
```

Реальный вывод (из `python examples/demo.py`):

```
diff: new=1 fixed=4 same=0 -> reports/diff.json
```

Сопоставление идёт по `fingerprint` (`детектор:файл:строка:заголовок`), поэтому
находка, которая просто сдвинулась на другую строку, помечается как *moved*, а не
как «исправлено + новая».

## 5. Очередь задач для исправления

Scout сам ничего не правит. Но может разложить находки по файлам-задачам, которые
затем возьмёт человек или ИИ-агент:

```sh
cd ~/projects/my-app                                   # очередь создаётся здесь
python /path/to/scout/tools/queue.py /path/to/reports/<прогон> --severity high
```

| Флаг | По умолчанию | Смысл |
|---|---|---|
| `--severity` | `high` | порог: `critical`, `high`, `medium`, `low` или `all` (берёт этот уровень **и выше**) |
| `--detector` | все | только один детектор, например `--detector mypy` |
| `--limit N` | без лимита | не больше N задач |
| `--queue DIR` | `.scout-queue` | куда класть |
| `--project DIR` | `.` | корень проекта: по нему подбираются команды проверки |
| `--dry` | выкл. | только показать, что будет создано |

Задачи ложатся в `.scout-queue/pending/task-<id>.md`. Повторный запуск
безопасен: существующие задачи не перезаписываются. В каждой задаче есть файл
и строка, evidence, предложение и команды проверки (`verify`). Когда исправление
сделано, файл переносят в `.scout-queue/done/`, а если не получилось, то в
`.scout-queue/rejected/`.

> Добавьте `.scout-queue/` в `.gitignore` проекта, если не хотите коммитить очередь.

Команды `/scout-pick`, упоминавшейся раньше в README, в этом репозитории **нет**:
Scout ничего не правит, а отдельного «исправляющего» скилла здесь пока не поставляется.
Файл задачи самодостаточен (в нём шаги, команды проверки и правила), поэтому подойдёт
любой агент. Например, в Claude Code в каталоге проекта:

```
Возьми самую старую задачу из .scout-queue/pending/, покажи её мне и, после моего
подтверждения, выполни ровно то, что в ней написано. Правь только указанные файлы,
прогони команды из verify, не делай git push. Если проверка падает, откати свои правки
и перенеси задачу в .scout-queue/rejected/.
```

## 6. Работа через Claude Code / Cursor / Codex

Scout можно запускать как скилл: агент сам пройдёт фазы 0–4 (проверка, скан,
отсев, предложения, дашборд).

```
/scout ~/projects/my-app
```

или словами: «просканируй проект», «найди баги», «проверь проект на уязвимости».
Быстрый проход: `/scout quick ~/projects/my-app`.

Как это устроено:

- `SKILL.md` описывает фазы, правила чтения лежат в `phases/` (агент читает по одному файлу за раз).
- `CLAUDE.md`, `AGENTS.md` и `.cursor/rules/` — тонкие адаптеры под конкретного агента.
- Скилл вызывает те же скрипты из `tools/`, поэтому результат совпадает с ручным запуском.

### Установка как скилла

Проверено 2026-10-13 с пакетом `skills` 1.7.2 (vercel-labs):

```sh
cd ~/projects/my-app
npx skills add Alpha-Oi/scout -a claude-code     # в этот проект
npx skills add Alpha-Oi/scout -a claude-code -g  # для всех проектов (~/.claude/skills)
```

Что при этом происходит:

- CLI клонирует репозиторий (ветка по умолчанию) и находит один скилл: `scout`.
- Копирует **весь** репозиторий в `./.claude/skills/scout/` (нужны `SKILL.md`,
  `phases/`, `tools/`, `scripts/`; остальное, например `docs/`, лежит рядом и не мешает).
- Создаёт в проекте файл `skills-lock.json` (учёт установленных скиллов).
- Полезные флаги: `--list` (только показать), `--copy` (копии вместо симлинков),
  `-y` (без вопросов), `-a cursor` / `-a codex` для других агентов.
- CLI отправляет анонимную телеметрию; отключить: `DISABLE_TELEMETRY=1`.
- Обновить: `npx skills update`, удалить: `npx skills remove scout`.

Скилл выполняется с полными правами агента: перед установкой посмотрите содержимое
репозитория, как и для любого стороннего скилла.

**Про пути.** В `SKILL.md` и `phases/` инструменты названы как `tools/scan.py`. Это
пути **от папки скилла**, а не от вашего проекта (рабочий каталог агента это ваш
проект, там `tools/scan.py` нет). Поэтому в `SKILL.md` прописано правило: запускать
по полному пути, например `python .claude/skills/scout/tools/scan.py <проект> --out ./.scout`.
Отчёты при этом по-прежнему идут в `./.scout` вашего рабочего каталога, а не в сканируемый проект.

Ручная установка: скопируйте репозиторий целиком в `.claude/skills/scout/` (или
в каталог скиллов вашего агента). Проверить целостность:
`python .claude/skills/scout/scripts/verify-skill.py` должен вывести `scout check: OK`.

## 7. Предложения через LLM (необязательно)

По умолчанию предложения формируются **правилами**, без сети и детерминированно:
одинаковые находки дают одинаковый текст. Для более развёрнутых советов:

```sh
python tools/propose.py ./reports/<прогон> --llm --llm-max 20
```

Провайдер выбирается автоматически: `ANTHROPIC_API_KEY`, затем `OPENAI_API_KEY`,
затем локальный Ollama на `127.0.0.1:11434`. Если ничего не найдено, Scout
откатывается на правила. Ответы кэшируются в `.scout-llm-cache.json`.

> ⚠️ С `--llm` фрагменты кода из находок уходят внешнему провайдеру (кроме
> Ollama, он локальный). Для закрытых проектов используйте Ollama или не включайте флаг.
